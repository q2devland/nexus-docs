Docker image

Nexus ships as one Docker image, which runs one Project: the API, under /api, the web app that calls it, and this documentation, under /docs, as it is for the image’s version, all from the same origin and port. All it needs besides is a PostgreSQL database, and somewhere to keep Files: a volume of its own, or a bucket of a cloud provider. Each Project is its own container, with its own database.

Pulling it

Section titled “Pulling it”

Each release of Nexus publishes the image to GitHub’s container registry, GHCR, as ghcr.io/q2devland/nexus, tagged:

  • with its version, such as ghcr.io/q2devland/nexus:1.4.0, which never changes;
  • latest, the newest release, which does.

Deploy a version, never latest: what runs then changes only when you change it. See Upgrading.

The image is private, as Nexus’s repository is. Log in to GHCR first, as a GitHub user who may read it, with a personal access token that has the read:packages scope as the password:

Docker keeps the login, so the machine that runs Nexus logs in once.

Running it

Section titled “Running it”

nexus.env holds its configuration, as environment variables; two are required, the database and the secret that signs access tokens:

and a Project people sign in to needs its first admin, an Identity provider and its public URL. The Configuration reference has every variable. Docker Compose runs the image with its database, and its whole configuration.

On start, Nexus brings the database up to date with its version, then listens: a database it can’t reach, or a variable it can’t use, stops it, saying why. See Database.

Its port and volume

Section titled “Its port and volume”
  • Port 3000: the web app, the API and the documentation, over HTTP. NEXUS_PORT moves it: publish the one it sets, such as -p 8080:8080 with NEXUS_PORT=8080.
  • Volume /data/files: the Files people upload, while NEXUS_STORAGE keeps them on disk, as it does unless set. Mount a named volume, or a folder of the host the user node (1000) may write to; a container without one loses its Files when it’s removed. One kept in the cloud needs no volume. See File storage.

It also sets:

Variable Value
NEXUS_PORT 3000
NEXUS_WEB_ROOT /app/web, the web app
NEXUS_DOCS_ROOT /app/docs, the documentation
NEXUS_STORAGE_PATH /data/files
NODE_ENV production

It runs as the user node, never root, from /app, on Node.js 24, and checks its own health every 10 seconds, through /api/health: docker ps shows it healthy, or unhealthy while its database doesn’t answer. Nexus logs its warnings and errors to the container’s output, which docker logs nexus shows.

Its documentation

Section titled “Its documentation”

The image serves this documentation as it is for its own version, under /docs, such as https://cms.reelhouse.example/docs/: what the Project runs, even once later releases change it. Its pages say which version they describe, and link to the same page of the latest, on q2devland.github.io/nexus-docs. Anyone reaches them, signed in or not, as anyone reaches the latest; search engines are asked to leave them out. The web app links to them, from the sections’ rail on a computer and the More sheet on a phone.

A Project that wants no /docs sets NEXUS_DOCS_ROOT empty: then nothing is served there, and the web app’s link opens the latest instead.

Behind a proxy

Section titled “Behind a proxy”

Nexus speaks HTTP: something in front of it ends TLS, such as a reverse proxy on the same host, a load balancer or the platform’s ingress, and forwards to its port. Nexus sends Strict-Transport-Security, and marks its cookies Secure once people reach it over HTTPS, as they must.

A proxy on the same host or a private network is trusted to say what people used: it passes on the Host they asked for, and sets X-Forwarded-Proto and X-Forwarded-For, overwriting what the client sent. Nexus then builds its addresses, those Identity providers send people back to and those Invitations link to, from the request, and limits requests by the client’s address. A proxy anywhere else isn’t trusted: set NEXUS_PUBLIC_URL, such as https://cms.reelhouse.example, and Nexus uses that.

Extensions

Section titled “Extensions”

The image holds no Extension: mount each one’s folder, built, with its dependencies installed, and list it in NEXUS_EXTENSIONS:

Or build an image of your own FROM ghcr.io/q2devland/nexus:1.4.0 that copies them in, so that each version of the Extensions is an image. They run on the image’s Node.js, on Linux: install their dependencies for it.

Several replicas

Section titled “Several replicas”

A Project may run several containers of the same image, behind one load balancer, all with the same configuration, Extensions and version, on the same database:

  • Their Files are kept where every one reaches them: a bucket of a cloud provider, or one volume they share.
  • Starting together, one brings the database up to date while the others wait.
  • Each counts its own rate limit, and rebuilds its share of the Read model.
  • Sessions are in the database: whichever answers, people stay signed in.

Its commands

Section titled “Its commands”

The image’s main.js also runs commands against the Project’s database, with the container’s configuration:

  • restore-admin <email> gives that person the Admin role, for when no admin can sign in; see The first admin.
  • purge-history deletes the history older than its Collection keeps it, as Nexus does every day; see History.
  • purge-files deletes the Files uploaded a day ago or more that no Item holds, as Nexus does every day.
  • model-export [<file>], model-diff <file> and model-apply <file> move the data model between Projects; see Model snapshots.
