Action handlers

An Action handler is a named entry point an Extension registers, which an Action runs instead of calling a URL: once for all the Items the Action is run on, with the values entered, while the User waits for its answer. Reelhouse’s count-episodes is what its Action Count episodes runs, on its TV shows.

Registering one

Section titled “Registering one”

actionHandlers names each, by any name not blank. Admins pick one for an Action, in its Call, among those of the Extensions loaded, as count-episodes · cinema-demo: its name, then its Extension’s. An Action keeps that name; one whose handler no Extension registers any more, or whose Extension is disabled, stays defined, hidden from those who run Actions and marked Handler unavailable for admins, until it’s back.

What it’s given

Section titled “What it’s given”

A handler is given the run first, what an Action’s call sends a URL:

  • action: the Action’s key, count_episodes.
  • collection: the Collection’s key, tv_shows.
  • items: the ids of the Items it’s run on, as text.
  • inputs: each value entered by its key, null for one left empty.
  • user: who ran it, their id and email.
  • language: their UI language, such as en-GB, to answer in.

Then its context: user, the User who ran it as hooks are told of them, items, db, files, config and logger, with signal and transaction.

Answering

Section titled “Answering”
  • Returning { message }, or nothing, is a success: the User sees Done., and its message, up to 500 characters. Count episodes answers The TV show has 11 episodes. of Wexmoor Tide, and The 4 TV shows have 30 episodes. of all four.
  • Throwing an ExtensionRefusal is a failure the User sees as It was refused., with its message: The TV show has no episodes.
  • Throwing anything else is a failure that says no more than It failed: something went wrong while it ran.: the error is logged, with its stack, as The Action handler cinema-demo/count-episodes failed, and the Delivery log keeps its message with the run.

Each run is kept in the Delivery log, with its Items, how it went, its message and how long it took, unless the Action isn’t logged. A run is never retried: the User runs it again.

Transactions

Section titled “Transactions”

A handler runs outside any transaction. Each write through its items is a transaction of its own, as an API request’s is, with its write hooks and Webhooks, as the User’s Role allows unless bypassingPermissions(); a handler that writes several Items and stops halfway leaves those written before.

transaction(work) runs work in one transaction, acting as the User who ran the Action, whom the History names: it’s given the items and the db of that transaction, which commit together once work ends, or roll back if it throws. It answers what work answers.

Timeouts

Section titled “Timeouts”

The User waits for a handler as long as the Action’s Timeout says, 60 seconds unless an admin gives it less. Once it’s over, the User is told It failed: it took too long to finish., and the handler’s signal is aborted. Nexus stops nothing: what it committed by then stays, and stopping is its own job.
