The hook context

Every Extension hook and Action handler is given a context to do its work with: who it works for, the Items, the database, the Files, its settings and a logger. Each destructures what it needs, as Reelhouse’s Action handler and read hook do:

What a write hook is given of the write (operation, payload, previous, item) and a read hook of the read (read, id, found) is on their pages; an Action handler’s run is on its own.

user

Section titled “user”

The User the write, the read or the run is for: who signed in, or the API user whose token called.

  • id, email and name; an API user has no email.
  • api: whether an API user, which calls with its API tokens and never signs in.
  • role: their Role’s id, name and whether it’s admin.
  • language: their UI language, such as en-GB.

cinema-demo keeps films from API users, telling them by api, and speaks the language of who ran its Action:

A write an Extension makes runs as that User: its created_by and updated_by, and the History, name them.

items

Section titled “items”

The Items, read and written as the User’s Role allows, through Nexus as the API does: with validation, Field conditions, the Extension hooks of each write and its Webhooks, queued for the Read model.

  • one(collection, id): the Item with that id, or undefined when there’s none.
  • page(collection, query): a page of Items, { items, total }, as GET /api/items/<collection> answers it. query takes filter, in the filter language, its paths through Translations reading them in the default Content language, sort, a Field key or a part of a date Field, year(released_on), after - for descending order, or several between commas, search, ids, offset, limit, 500 at most, 100 unless given, and timezone, which the filter and the sort read a timestamp’s parts in, UTC unless given.
  • create(collection, values), update(collection, id, values) and delete(collection, id), with values as the Items API takes them, answering the Item written.
  • bypassingPermissions(): the same Items, read and written as an Admin role would, every Collection and Field. The History and the Items’ created_by and updated_by still name the User.

Counted that way, Count episodes would tell a User of episodes their Role doesn’t read: bypass permissions only for what the User may know of, such as a total kept for every Role alike.

count-episodes counts a TV show’s episodes as the total of a page of one, filtered through their seasons:

Reading through items runs no read hooks: an Extension sees what the Role allows, past them. Reading as the User, rather than bypassing permissions, is what keeps a handler from telling a Viewer about Items their Role doesn’t read.

What items writes from a write hook goes at most 5 writes deep, each from a hook of the write before; deeper, the whole write is refused.

db

Section titled “db”

The database itself, a Kysely instance, past every rule of Nexus: no Extension hooks, validation, permissions nor Webhooks see what is written through it. It’s the documented way past them, for what the Items can’t say or would make slow: a bulk recalculation, a report, tables of the Extension’s own.

An Action of seasons might set the runtime of all their episodes in one statement, in a transaction acting as the User:

The database still holds to its own rules: the History records what’s written, under the User when written in a transaction Nexus opened; changes are queued for the Read model; and an Item is written with who creates, changes or deletes it, in its created_by or updated_by, or the transaction’s nexus.user, unless the Project settings say otherwise.

files

Section titled “files”

The File library:

  • read(id): the File with that id, its name, title, type, size, width and height, with its bytes as content; it rejects when there’s none.
  • create({ collection, field, name, type, content }): a new File, from bytes or text, as an upload through that File or Image Field, which the User must be able to write. An image’s type is told by its content. It answers the File; holding it in the Field is writing its id there.

config and logger

Section titled “config and logger”

config is the Extension’s settings, from its NEXUS_EXTENSION_<NAME>_* variables: see Configuration.

logger writes to Nexus’s log, under Extension <name>: log, warn, error, with the error itself, whose stack it logs, and debug.

In a write, a read and an Action handler

Section titled “In a write, a read and an Action handler”
Write hook Read hook Action handler
Transaction The write’s own: everything it does commits or rolls back with it None None; transaction(work) opens one
items Reads and writes, in the write’s transaction Only reads Reads, and writes each in a transaction of its own
db The write’s transaction The database The database
files Reads and creates Files Only reads Reads and creates Files
Besides operation, collection, payload, previous, item read, collection, id, found signal, transaction

A write hook’s db is the write’s own transaction: what it writes there commits with the Item, or rolls back with it. A read hook’s and an Action handler’s db is the database, where every statement commits on its own; an Action handler’s transaction(work) gives work the items and the db of one transaction, acting as the User.
