Authentication

Every call to the API names its caller with a token, in the Authorization header:

Only signing in, the health check and the Project’s branding, which the sign-in page shows, are open without one. A call without a token, or with one that doesn’t let it in, is refused before anything else is looked at.

API tokens

Section titled “API tokens”

A system, such as a website build, an import script or a deployment pipeline, calls the API as an API user, with one of its API tokens: a secret beginning nx_, created by an admin in Users › API users, and shown once. Reelhouse’s website build reads its catalogue as Website build, a Viewer, with its token Production:

Keep the token where the system keeps its secrets, here the NEXUS_TOKEN variable, never in its code. A token works until it expires, if it has an expiry, or is revoked, and only while its API user is active: revoking it, or deactivating its API user, stops it from the next call on. See Expiry and revoking.

People can’t have API tokens. Give each system an API user of its own, with a Role that allows exactly what it needs: Reelhouse’s website build reads, and needs no more than a Viewer.

Access tokens

Section titled “Access tokens”

A User who signs in to the web app calls the same API with short-lived access tokens, valid for 15 minutes unless the deployment sets NEXUS_ACCESS_TOKEN_LIFETIME, which the browser gets from Nexus with the session it keeps in a cookie, and sends the same way. They’re the web app’s own, and stop when the session ends; a script never asks for one, but calls as an API user. See How sign-in works.

What a token may do

Section titled “What a token may do”

A call may do what its User’s Role allows, and nothing else, whoever the User is: an API user’s Role says what its tokens may do, exactly as a person’s says what they may do in the browser.

  • Collection permissions say which Collections’ Items it may read, create, update and delete.
  • Field permissions hide Fields from it, and keep it from writing others: an Item answers without the Fields hidden from its Role, which it can’t filter, sort or select through either.
  • File folder permissions say which Files it may view, replace and delete.
  • An Admin role may do everything, changing the model, the Users and the Project settings too.

So Website build may read every Collection of Reelhouse, but no more:

What a call writes is recorded as its User’s doing: the Items it creates and changes name it in their created_by and updated_by, and their History under its name. See Who writes.

When a token isn’t let in

Section titled “When a token isn’t let in”
Status When
401 No Authorization header, a scheme other than Bearer, or a token that isn’t one: unknown, revoked, expired, of an inactive API user, or of a session that has ended
403 A token let in, whose Role may not do what the call asks

A 401 says nothing more, whatever the reason, so that a token can’t be probed:

A system that gets one has a token to replace: create another, give it to the system, then revoke the old one.

From a browser

Section titled “From a browser”

A page on another origin that calls the API with a token, such as a website reading Reelhouse from its visitors’ browsers, needs that origin allowed in NEXUS_CORS_ORIGINS, or * for any: none is by default. It may send a token, but never the session’s cookie. An API token in a page is readable by anyone who opens it, so give such a page an API user that only reads what the page shows, or read through its own server instead.
