Upgrading

Upgrading a Project is running a newer image of Nexus on its database: the new version brings the database up to date with itself as it starts, and runs. Each Project is upgraded on its own, when its deployment says, never by Nexus itself.

Versions

Section titled “Versions”

Each release of Nexus has a version, major.minor.patch, such as 1.4.0, which tags its Docker image and its SDK:

  • A major version, 2.0.0, may change what Extensions are built against: Nexus loads only those built against the SDK of its own major version.
  • A minor or patch version, 1.5.0 or 1.4.1, loads the Extensions of its major version, built against an earlier one among them.

Each version’s release notes say what changed in it, and what a deployment must do about it. Upgrading several versions at once is fine: the newest one brings the database up to date from wherever it is. Read the notes of every version in between.

Before upgrading

Section titled “Before upgrading”
  • Read the release notes of each version from yours to the new one, for what to change first.
  • Back up the database and the Files: the only way back to the version before is restoring them. See Backups.
  • Try it first on a copy, such as staging, restored from that backup, when the new version is a major one, or the Project has Extensions.

Compose stops the Nexus that runs, and starts the new one on the same database, volumes and configuration. As it starts, the new one runs its migrations, then answers once more; up --wait returns once it’s healthy. People see Nexus unavailable meanwhile, a few seconds, or longer when a migration has much to change, and sign in no more than before: their sessions stay.

Should a migration fail, it changes nothing: the database is left as the earlier version had it, and the new Nexus doesn’t start, its log saying why. Go back to the earlier NEXUS_VERSION, which starts on it as before, and report it.

Several replicas

Section titled “Several replicas”

Stop every replica of the earlier version before starting the new ones: an earlier one isn’t made for the database once the new one has migrated it. The new replicas may start together: one migrates, while the others wait.

Extensions

Section titled “Extensions”

An Extension built against the SDK of the same major version loads in the new one, a minor or patch release later. Upgrading to a new major version is upgrading the Extensions with it: build each against the SDK of that version, change what its release notes say changed, and deploy them together, as Nexus refuses to start with one built against another major version. See Writing an Extension.

Going back

Section titled “Going back”

Migrations only go forward: an earlier version refuses to start on a database a later one has migrated, saying that a migration it ran is missing. Going back is stopping Nexus, restoring the backup made before upgrading, and starting the version it was made with, which loses what people did since.
