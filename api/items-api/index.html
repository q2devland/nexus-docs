Items API

Each Collection’s Items are at /api/items/<collection>, by the Collection’s key, as soon as it exists. They’re read and written as the caller’s Role sees them: without the Fields hidden from it, and only as its Collection permissions allow.

Request What it does
GET /api/items/<collection> A page of its Items
POST /api/items/<collection> Creates an Item, answered with 201
GET /api/items/<collection>/<id> One Item
PATCH /api/items/<collection>/<id> Changes the values given of an Item
DELETE /api/items/<collection>/<id> Deletes an Item, answered with 204
POST /api/items/<collection>/delete Deletes several, each as DELETE would
GET /api/items/<collection>/<id>/related/<field> The Items a Relation links, or the Translations of a Translations Field
GET /api/items/<collection>/<id>/history Its History, newest first
GET /api/items/<collection>/<id>/link-counts How many Items each many-relation its Field conditions count links, { "genres": 3 }
GET /api/items/<collection>/<id>/preview Where it’s previewed, by its Collection’s Preview URL
POST /api/items/<collection>/csv Its Items as a CSV file, as Export to CSV makes it

An id that names no Item answers 404, and so does a key that names no Collection. The examples are Reelhouse’s, as pnpm demo runs it, with a token in NEXUS_TOKEN; see Authentication.

Reading Items

Section titled “Reading Items”

A page of a Collection’s Items, the latest films first:

total counts every Item the query keeps, not only those of the page. Each Item answers its Fields that store a value by their keys: its own and the System fields, a File or Image Field as its File’s id, a Repeater as its Rows, an Image URL as { "url": "films/paper-comets.png", "name": "paper-comets" }, its URL as entered, a Video key as { "site": "reelhouse-player", "key": "paper-comets", "name": "Paper Comets: trailer" }. Its Relations don’t answer unless asked for, through fields.

A page takes:

Parameter What
filter Keeps the Items that pass a filter, as JSON; see Filtering and sorting
sort Their order, by Fields between commas, - before one for descending, or by a part of a date Field, -year(released_on); by id when left out
search Keeps those with a Searchable field that contains it, whatever its case and accents, theirs or their Translation’s in language
offset, limit The page: from 0 and 100 Items when left out, at most 500
fields What each Item answers; see Choosing what each Item answers
language The code of the Content language its Translations are read in, by paths and by Display texts; the default one when left out
timezone The IANA timezone, such as Europe/Madrid, that filter, sort and $display read a timestamp’s parts in; UTC when left out
display true adds $display: each Item shown by its Collection’s Display template, such as The Saltmarsh Inheritance (2021), with the values of the related Items it reaches, and of its Translation in language, nothing without one; a part of a date as a number, a month and a weekday by name in the UI language of the User whose token calls, English without one, a timestamp’s in timezone
id, exclude Keeps only, or leaves out, the Items with these ids, the parameter repeated for each

One Item, GET /api/items/films/2, takes fields, language, timezone and display too, and its preview, GET /api/items/films/2/preview, language and timezone, which a Preview URL’s parts of a timestamp are read in.

Choosing what each Item answers

Section titled “Choosing what each Item answers”

fields names what each Item answers, as paths between commas, or the parameter repeated:

  • *, as by default: its own Fields that store a value.
  • A Field’s key: that Field only. Its id answers only if named.
  • A Relation’s key: the ids it holds, a Many to One’s one id, a many-relation’s list of them, a Translations Field’s its Translation’s id in language.
  • A path through a Relation, at any depth: the related Items as the rest of the path selects them, under the Relation’s key. genres.name answers each genre’s name, genres.* each genre whole, cast.name each person’s name, seasons.episodes.title each season’s episodes’ titles.
  • A Many to Any’s path names the Collection it goes into: featured:films.title. An Item of its other Collections answers as a reference, { "collection": "tv_shows", "id": 3 }.
  • translations.title: the Item’s Translation in language, or translations:es.title in the Content language its step names, answered under translations:es; null without one.
  • created_by.name and updated_by.name: the name of who created or last changed it, created_by.id their id. Nothing else of a User is ever answered.
  • $display: the Item shown by its Collection’s Display template, as display=true adds it. At the end of a path through a Relation, the related Item shown as the Relation shows it, by the Relation Field’s own Display template if it has one: season.$display answers an episode’s season as Season 1.

A one-to-many or many-to-many path answers the related Items in the order of their links, a Many to One’s one Item or null. A path to a Field the Collection lacks, or that the caller’s Role can’t see, is refused, with invalid-fields at fields.<index>, and so are more than 100 paths.

Relations

Section titled “Relations”

An Item’s Relations are read, a page at a time, at /related/<field>, which takes the parameters a page of their Collection takes, and its writes change them, as the Item’s own values. A Many to One is no list: it’s a value of the Item, the id of the Item it refers to, written as any other.

Reading links

Section titled “Reading links”

The cast of The Saltmarsh Inheritance, as films_cast links its people, the first two in its order:

  • A sorted Many to Many’s, or a Many to Any’s, come in the order of their links; an ordered One to Many’s by the Field it’s ordered by; others by id. sort orders them otherwise.
  • Through a Junction collection with Fields of its own, as films_cast, each Item has its link’s values under $link: the character played, a Many to One to characters, and the billing order.
  • A Many to Any’s Items, of several Collections, each have the key of theirs under $collection: the homepage’s featured answers films and TV shows. They take offset, limit and display alone, unless collection=films keeps those of one of its Collections, which then take every parameter.
  • linked=false answers the Items of the target the Relation doesn’t link instead, as a picker offers them.

Reading the Items a Relation leads to needs reading their Collection too.

Linking and unlinking

Section titled “Linking and unlinking”

A write gives a One to Many, Many to Many or Many to Any Field what changes in its links, applied in this order:

Key What
move Places Items it links at positions among all of them, from 0: { "id": 7, "to": 0 }, only for a sorted Many to Many or Many to Any, or a One to Many ordered by a Field
unlink Removes the links to these Items
link Adds links to these Items, at the end in that order, leaving be those it has
update Changes the values of links it has, through a Junction collection with Fields of its own

A Many to Any names its Items as references, { "collection": "films", "id": 7 }. Through a Junction collection with Fields of its own, link and update name an Item with the values of its link, { "id": 7, "values": { "character": 4, "billing_order": 1 } }, checked as an Item of that Junction collection is; a link created without them takes their defaults. Linking through a One to Many sets the linked Item’s Many to One to this Item, taking it from any other, and unlinking empties it, which a Many to One that can’t be empty refuses.

sent as PATCH /api/items/homepage/1. An id that names no Item of the target is refused, with not-found at the Field’s key, and so is a move of an Item it doesn’t link, with wrong-type.

Translations

Section titled “Translations”

A Translations Field’s value is the Item’s Translations, by the code of each Content language: the values of that language’s Translation, as an Item of the Translations collection takes them, or null to remove it, a One to Many, Many to Many or Many to Any Field of it taking link changes for that Translation’s links. A Translation with no value in any of its Fields that hold one is removed, or not created, whatever links it is given.

Every mandatory language needs a Translation whenever an Item is created or changed, whatever the write gives: Reelhouse’s films can’t be saved without their English one. The Translations are read at /related/translations, each with its Content language’s id under language, or through fields, translations.title in the language asked for.

Creating an Item

Section titled “Creating an Item”

POST /api/items/<collection> creates an Item from its values, by key, and answers it, with 201. Fields left out take their default value; Nexus fills in the System fields, but the id of a Collection keyed by text, which the request gives.

Its links and Translations are written with it, in the same transaction: a problem with any of them saves nothing. A File or Image Field takes the id of a File uploaded through it first; see File and Image Fields. An Image URL takes { url, name }, the name optional: without one, it’s taken from the URL; see Image URLs. A Video key takes { site, key, name }, all three; see Video keys. A singleton that has its Item refuses another.

Updating an Item

Section titled “Updating an Item”

PATCH /api/items/<collection>/<id> changes the values it’s given, and only those, and answers the Item:

A value is checked as the Item view checks it: its Data type, its Interface’s limits, its Unique set, the Field conditions that make it required. A refused write answers every problem found, each at its Field’s key, and saves nothing; see Errors and limits.

Deleting Items

Section titled “Deleting Items”

DELETE /api/items/<collection>/<id> deletes an Item, answered with 204, and with it, by its Relations’ rules, the Items that refer to it through a Many to One that cascades, as a film takes its Translations; those that set null lose the reference. While an Item refers to it through one that restricts, it’s refused with 409 and referenced: Reelhouse’s Content language Spanish can’t be deleted while Translations are in it.

POST /api/items/<collection>/delete, with { "ids": [7, 12] }, at most 500, deletes each in turn as DELETE would, and answers what became of each: those deleted, those missing, and those refused, with why. One refused leaves the others to be deleted.

Who writes

Section titled “Who writes”

Every write names who makes it: the caller. The Items it creates name its User in created_by, those it changes in updated_by, the database stamps when in created_on and updated_on, and the Item’s History records the change under its name, an API user’s as a person’s. created_by and updated_by can’t be written, so a write never names anyone else:

Extensions

Section titled “Extensions”

The Project’s Extensions run around the Items API’s reads and writes as around the web app’s: a write hook may change an Item before it’s saved, as Reelhouse’s tidies a film’s title, or refuse it, answered with 422 and its own words; a read hook may narrow what a read finds. A write that saves Items starts the Webhooks that wait for it, as Reelhouse’s Film published does, and queues them for the Read model.
