OpenAPI

Every Project describes its API in an OpenAPI 3.1 document, at /api/openapi.json, generated from its model each time it’s asked for: a Collection created a moment ago is in it, with its Fields, and one deleted is gone. Load it into any tool that reads OpenAPI to browse the API, try its calls, or generate a typed client from it.

It needs a token, as every call does, and describes the API as its caller sees it: only the Collections its Role reads, each Item without the Fields hidden from it, and only the writes it may make. Two callers with different Roles get different documents. Reelhouse’s admin’s describes 94 operations; Website build’s, a Viewer, only the 49 that read, without a single create, update or delete, and without the schemas of what it would write.

What it describes

Section titled “What it describes”

For each Collection the Role reads, by its key:

  • GET /api/items/<collection>, a page of its Items, with every parameter a page takes, and GET /api/items/<collection>/{id}, one of them;
  • POST, PATCH and DELETE, where the Role may create, update and delete its Items;
  • its Items’ history, and their preview where the Collection has a Preview URL;
  • the schema of its Items, films, as the API answers them: each Field by its key, of its Data type, described by its description, or its name, in English; its Relations as their ids, or the related Items fields selects; and, for each write it may make, what the write takes, films.create and films.update, the Fields that need a value and have no default required to create one;
  • what each route may refuse, with the schema of the refusal.

And the Read model’s routes, GET /api/content, POST /api/content/query and GET /api/content/{id}, with the schemas of its queries and entries. The shared schemas, such as LinkChanges, TranslationChanges, ItemRefusal and ItemQueryProblem, are those described in Items API and Errors and limits.

The document names its routes in full, from the address it’s read at, and its one security scheme is the bearer token of Authentication.

Keeping a client up to date

Section titled “Keeping a client up to date”

The document changes whenever the model does, or the caller’s Role. A client generated from it, such as the types of a website’s build, is generated again after a model change, from the document of the API user it calls as, so that it describes what that API user may do. Apply a Model snapshot to a staging Project first and generate from there, so that the client is ready before the model reaches production.
